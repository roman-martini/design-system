# Registro de decisiones de producto

Decisiones de producto/negocio del design system, resueltas con el product owner (Roman). **Append-only**: las decisiones no se editan ni se borran; si una cambia, se agrega una nueva y la vieja se marca como _Reemplazada por D-YYY_. Las decisiones técnicas van como ADR en `docs/architecture/adr/` (las D-XXX enlazan al ADR cuando la ejecución técnica vive allá).

> Las D-001…D-007 se registraron el 2026-07-10 al crear este espacio, **documentando decisiones ya tomadas** durante el bootstrap y los changes aaa-001…aaa-014. La fecha de la columna es la de la decisión original.

| #     | Fecha      | Tema                       | Decisión                                                                                                                                                                                                                                                                                                                                                                                               |
| ----- | ---------- | -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| D-001 | 2026-05-29 | Alcance del producto       | El producto es un **design system para frontend Angular**: `@romanmartinidev/tokens` + `@romanmartinidev/components` como libs publicables. `apps/playground` es **laboratorio interno no publicable** para validar las libs y crear prototipos exportables a proyectos reales. Fuente: [contexto_inicial](../contexto_inicial.md).                                                                    |
| D-002 | 2026-05-29 | Prioridades de producto    | Toda decisión se justifica contra tres prioridades **en orden estricto**: (1) buenas prácticas, (2) diseños/arquitecturas que escalen ordenado, (3) mantenibilidad vía estándares. Ante disyuntivas no se elige por velocidad.                                                                                                                                                                         |
| D-003 | 2026-05-30 | Consumidor y distribución  | Consumidor v1: **los proyectos propios de Roman**. Distribución vía **npm público** bajo el scope `@romanmartinidev` (`access: public`) — terceros pueden instalar, pero pre-1.0 no hay compromiso de soporte externo.                                                                                                                                                                                 |
| D-004 | 2026-05-30 | Estabilidad pre-1.0        | Mientras los packages estén en `0.x`, la **superficie API puede cambiar** respetando semver. La política definitiva de estabilidad se acuerda al primer release 1.0 (pendiente, ver EP-003).                                                                                                                                                                                                           |
| D-005 | 2026-06-08 | Sin features hipotéticas   | Ninguna capacidad (componente, token, tooling) entra al kit "por completitud": entra cuando hay **disparador o caso de uso real**. FUTURE-WORK es inspiración; el BACKLOG exige disparador.                                                                                                                                                                                                            |
| D-006 | 2026-06-09 | El código define el diseño | La **fuente de verdad del lenguaje visual es el repo** (tokens en código). Figma/diseño **consume** — nunca define de vuelta de forma automática (one-way code→design). Ejecución técnica: [ADR-009](../architecture/adr/ADR-009-figma-tokens-export.md).                                                                                                                                              |
| D-007 | 2026-07-03 | Accesibilidad como feature | La a11y es **parte del valor del producto, no un extra**: patrones accesibles se adoptan aunque cuesten más código (disabled accesible [ADR-011](../architecture/adr/ADR-011-estado-disabled-accesible.md), a11y de plataforma en overlays [ADR-013](../architecture/adr/ADR-013-overlays-dialog-nativo.md), reglas a11y de iconografía [ADR-012](../architecture/adr/ADR-012-iconografia-lucide.md)). |
