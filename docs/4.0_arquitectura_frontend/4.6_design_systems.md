## Qué es un Design System

Un Design System es la **infraestructura compartida** entre diseño y desarrollo. No es solo una librería de componentes ni solo una guía de estilo — es el conjunto de decisiones, herramientas y procesos que permiten a múltiples equipos construir productos consistentes sin coordinarse en cada detalle.

```
Design System
├── Foundation (tokens, tipografía, colores, espaciado)
├── Component Library (átomos, moléculas, organismos)
├── Documentación viva (Storybook, guías de uso)
├── Procesos (cómo se propone, revisa y publica un cambio)
└── Gobernanza (quién decide, cómo evoluciona, cómo se versiona)
```

**La distinción importante:** un design system no es lo mismo que una guía de estilo. Una guía de estilo documenta el pasado. Un design system es infraestructura activa que equipos usan y contribuyen en tiempo real.

## 1. Design Tokens — la columna vertebral

Los tokens son las decisiones de diseño expresadas como variables. Son el contrato entre diseño y desarrollo.

### Sistema de 3 capas

```
primitives/   →  valores RAW sin semántica
semantic/     →  roles — los únicos que se usan en componentes
component/    →  tokens de scope de componente (opcional)
```

#### Capa 1: Primitivos

Valores absolutos sin contexto de uso. No se usan directamente en componentes.

```json
// primitives/color.json
{
  "color": {
    "neutral": {
      "50":  "#f8f9fa",
      "900": "#212529",
      "950": "#0d0f12"
    },
    "blue": {
      "500": "#3b82f6",
      "600": "#2563eb"
    }
  }
}
```

```css
/* Generado */
--rd-color-neutral-50: #f8f9fa;
--rd-color-neutral-900: #212529;
--rd-color-blue-500: #3b82f6;
```

#### Capa 2: Semánticos

Asignan un **rol** a los primitivos. Son los únicos que se usan en CSS de componentes.

```json
// semantic/index.json
{
  "color": {
    "text": {
      "primary":   { "value": "{color.neutral.900}" },
      "secondary": { "value": "{color.neutral.600}" }
    },
    "bg": {
      "base":      { "value": "{color.neutral.50}" },
      "primary":   { "value": "{color.blue.500}" }
    }
  },
  "space": {
    "sm": { "value": "{dimension.8}" },
    "md": { "value": "{dimension.16}" },
    "lg": { "value": "{dimension.24}" }
  }
}
```

```css
/* Generado */
--rd-semantic-color-text-primary: var(--rd-color-neutral-900);
--rd-semantic-color-bg-base:      var(--rd-color-neutral-50);
--rd-semantic-space-md:           var(--rd-dimension-16);
```

#### Capa 3: Component tokens (opcional)

Tokens de scope de componente. Permiten customización sin romper el sistema.

```css
/* Solo en button.css */
--rd-button-bg:           var(--rd-semantic-color-bg-primary);
--rd-button-bg-hover:     var(--rd-semantic-color-bg-primary-hover);
--rd-button-radius:       var(--rd-semantic-radius-md);
--rd-button-padding-x:    var(--rd-semantic-space-md);
```

El consumidor puede sobreescribir `--rd-button-bg` sin romper el sistema semántico.

### Regla de uso estricta

```css
/* ✅ Correcto — usa semántico */
color: var(--rd-semantic-color-text-primary);

/* ❌ Prohibido — usa primitivo directamente */
color: var(--rd-color-neutral-900);

/* ❌ Prohibido — valor hardcodeado */
color: #212529;
```

### Theming — dark mode y multi-marca

El sistema de capas hace el theming trivial: solo hay que sobreescribir los semánticos.

**Dark mode:**
```css
:root[data-theme="dark"] {
  --rd-semantic-color-bg-base:      var(--rd-color-neutral-950);
  --rd-semantic-color-text-primary: var(--rd-color-neutral-50);
  /* Los componentes no cambian nada — usan los semánticos */
}
```

**Multi-marca (en el proyecto consumidor):**
```css
/* brand.css — NUNCA en el paquete de tokens */
@import "@roman-dev/tokens/dist/tokens.css";

:root {
  --rd-semantic-color-text-primary:   #1a0a2e;
  --rd-semantic-color-bg-base:        #faf8ff;
  --rd-semantic-color-border-default: #d4c5f9;
}
```

El proyecto importa los tokens base y sobreescribe solo los semánticos. Los primitivos no se tocan nunca.

## 2. Component Library

La librería de componentes implementa los tokens y define la interfaz pública de los componentes.

### Arquitectura de componentes — Atomic Design

```
atoms/       ← unidades indivisibles: Button, Input, Icon, Badge
molecules/   ← composición de átomos: FormField, Card, NavItem
organisms/   ← composición de átomos + moléculas: Header, Modal, DataTable
```

**Reglas de dependencia estrictas:**
- Atom → no importa ningún otro componente
- Molecule → solo importa atoms, jamás organisms
- Organism → importa atoms y molecules

### Anatomía de un componente

Cada componente tiene un contrato de API explícito:

```typescript
// button.types.ts — primer archivo que define el componente
export type ButtonVariant = 'primary' | 'secondary' | 'ghost' | 'danger';
export type ButtonSize = 'sm' | 'md' | 'lg';

export interface ButtonProps {
  variant?: ButtonVariant;   // atributo enum — nunca múltiples booleans
  size?: ButtonSize;
  disabled?: boolean;
  loading?: boolean;
  onClick?: (event: MouseEvent) => void;
}
```

**Variantes como enum, no como booleans múltiples:**
```html
<!-- ✅ Correcto -->
<rd-button variant="primary">

<!-- ❌ Evitar — combinaciones exponenciales, difícil de documentar -->
<rd-button primary large outlined>
```

### CSS de componente

```css
/* button.css — solo tokens semánticos y de componente */
:host {
  display: inline-flex;
  container-type: inline-size;
}

button {
  background: var(--rd-button-bg, var(--rd-semantic-color-bg-primary));
  padding-block: var(--rd-button-padding-y, var(--rd-semantic-space-sm));
  padding-inline: var(--rd-button-padding-x, var(--rd-semantic-space-md));
  border-radius: var(--rd-button-radius, var(--rd-semantic-radius-md));
}
```

### Estados obligatorios

Todo componente interactivo documenta y expone:
- `default` — estado base
- `hover` — retroalimentación al puntero
- `focus` — visible para navegación por teclado
- `active` — click/tap
- `disabled` — no disponible
- `loading` — procesando (cuando aplica)
- `error` — estado inválido (cuando aplica)
- `empty` — sin contenido (cuando aplica)

## 3. Documentación viva

La documentación del design system es ejecutable — no estática. Storybook es el estándar:

```
src/
└── button/
    ├── button.ts
    ├── button.css
    ├── button.types.ts
    ├── button.stories.ts   ← una story por variante/estado
    └── button.test.ts
```

Cada story muestra el componente en un estado específico, con sus props documentadas y jugables en el panel de controles.

**Qué documenta cada story:**
- Variante o estado que representa
- Props disponibles con tipos y defaults
- Ejemplo de uso en contexto real
- Casos edge (texto muy largo, sin contenido, con íconos)

## 4. Versioning y gobernanza

### Semver para design systems

```
MAJOR.MINOR.PATCH
  │      │     └── fix de bug, corrección visual sin impacto en API
  │      └──────── feature nueva retrocompatible (token nuevo, variante nueva)
  └─────────────── breaking change (token renombrado, prop eliminada, comportamiento cambiado)
```

Un token renombrado es un breaking change — todos los consumidores que lo usen deben actualizar.

### Estrategia de deprecación

Nunca eliminar directamente. Proceso:

```
v2.1.0  → introducir --rd-semantic-color-text-primary
           deprecar   --rd-semantic-text-color (mantener como alias)
v3.0.0  → eliminar   --rd-semantic-text-color
```

El período de deprecación da tiempo a los consumidores para migrar.

### Modelos de gobernanza

| Modelo | Descripción | Cuándo |
|---|---|---|
| **Centralizado** | Un equipo dueño del DS, el resto consume | Design systems maduros, equipos grandes |
| **Federado** | Equipos contribuyen, un core team aprueba | Múltiples productos con necesidades distintas |
| **Distribuido** | Cualquiera contribuye sin gate central | Open source, equipos muy autónomos |

El modelo más común en empresas medianas es el **federado**: hay un equipo responsable que mantiene la calidad, pero los equipos de producto pueden proponer y contribuir componentes.

## 5. Cuándo vale la pena invertir en un Design System

Un DS tiene costo alto de creación y mantenimiento. Vale la pena cuando:

- **Múltiples productos o equipos** comparten la misma identidad visual
- **Alta frecuencia de UI nueva** — el tiempo de diseño/desarrollo de cada feature se amortiza rápido
- **Consistencia visible para el usuario** — el usuario navega entre productos y espera coherencia
- **Accesibilidad como requisito** — centralizar garantías de a11y en el DS es más eficiente que validar en cada producto

**No vale la pena cuando:**
- Es un producto único con un equipo chico
- El producto está en etapa exploratoria (el DS congela decisiones que todavía están cambiando)
- No hay capacidad de mantenerlo — un DS desactualizado es peor que no tener uno

---

## Señales de que el Design System está fallando

| Señal | Causa probable |
|---|---|
| Los equipos copian componentes en lugar de importarlos | La librería no cubre sus necesidades o es difícil de usar |
| Los tokens cambian pero los componentes no se actualizan | Falta de sincronización entre capas |
| Cada equipo tiene su propia versión del Button | Sin gobernanza o el proceso de contribución es muy lento |
| El DS está "terminado" y nadie lo toca | No hay proceso de evolución — se volvió legacy |
| Los diseñadores y devs tienen tokens diferentes | Diseño y código no están sincronizados (Figma tokens ≠ CSS tokens) |
