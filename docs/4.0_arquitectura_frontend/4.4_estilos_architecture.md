# CSS Architecture — Estrategias de Estilos

> Referencia rápida: [taxonomias_arq_software.md](../taxonomias_arq_software.md#44-estilos)

---

## El problema central

CSS es global por defecto. Un selector en cualquier archivo puede afectar cualquier elemento del DOM. Sin una estrategia deliberada, el resultado es especificidad incontrolable, colisiones de nombres y código que nadie se anima a tocar.

Las estrategias de CSS son distintas respuestas al mismo problema: **cómo aislar estilos, controlar la cascada y mantener consistencia a escala**.

---

## Estrategias de scope

### BEM (Block Element Modifier)

Convención de nomenclatura manual. Sin tooling, solo disciplina de equipo.

```css
.card { }
.card__title { }
.card__title--highlighted { }
.card--featured { }
```

- **Pros:** cero dependencias, funciona en cualquier stack, legible en DevTools
- **Contras:** verbose, se rompe con equipos grandes sin enforcement, anidamiento profundo se vuelve ilegible (`.nav__list__item__link--active`)
- **Cuándo:** proyectos sin bundler, legado, equipos que quieren control total sin tooling

### CSS Modules

El bundler transforma los nombres de clase en hashes únicos. El scope es por archivo.

```css
/* button.module.css */
.root { background: blue; }
/* Genera en build: .root_3xk2a { background: blue; } */
```

```tsx
import styles from './button.module.css'
<button className={styles.root}>
```

- **Pros:** scope real sin convención manual, ampliamente soportado (Next.js, Vite, CRA)
- **Contras:** composición entre módulos es incómoda, clases no legibles en producción sin sourcemaps
- **Cuándo:** React/Vue sin necesidad de estilos dinámicos por props en runtime

### Scoped Styles (Vue SFC)

Vue compila `<style scoped>` agregando un atributo único al HTML (`data-v-xxxxx`). Similar a CSS Modules pero integrado al Single File Component.

```vue
<style scoped>
.button { background: blue; }
/* Genera: .button[data-v-3xk2a] { background: blue; } */
</style>
```

- **Cuándo:** proyectos Vue — es el default natural

## Estrategias de dinamismo

### CSS-in-JS con Runtime (styled-components, Emotion)

Los estilos se escriben en JavaScript y se inyectan dinámicamente en el browser en cada render.

```tsx
const Button = styled.button<{ $primary: boolean }>`
  background: ${p => p.$primary ? 'blue' : 'white'};
  padding: ${p => p.$primary ? '12px 24px' : '8px 16px'};
`
```

- **Pros:** estilos dinámicos por props con type safety completo, colocación total con el componente
- **Contras:** **runtime overhead** — parsea y genera CSS en el browser en cada render. No funciona en React Server Components (RSC)
- **Cuándo:** apps puramente client-side donde el dinamismo por estado justifica el costo

### CSS-in-JS Zero Runtime (vanilla-extract, Linaria, StyleX, Panda CSS)

Mismo DX que CSS-in-JS pero los estilos se extraen a archivos `.css` estáticos en build time.

```ts
// vanilla-extract
import { style } from '@vanilla-extract/css';

export const button = style({
  background: 'blue',
  selectors: {
    '&:hover': { background: 'darkblue' },
  },
});
```

```ts
// StyleX (Meta) — garantiza que solo una clase gana por propiedad
const styles = stylex.create({
  base: { background: 'blue' },
  primary: { background: 'darkblue' },
});
```

- **Pros:** type safety completo, sin runtime overhead, compatible con SSR y RSC
- **Contras:** no podés usar variables JS dinámicas en runtime, setup más complejo
- **Cuándo:** design systems, apps con SSR/RSC, cuando querés type safety sin pagar runtime

## Estrategias de organización global

### CSS Layers (`@layer`)

Mecanismo nativo del browser para controlar el orden de la cascada explícitamente. Elimina la guerra de especificidad — el orden de declaración de layers determina quién gana, no la especificidad del selector.

```css
/* Declarar el orden primero — esto define quién gana */
@layer reset, tokens, base, components, compositions, utilities;

@layer components {
  .button { background: blue; } /* especificidad alta */
}

@layer utilities {
  .bg-red { background: red; } /* especificidad baja, pero en layer superior → GANA */
}
```

Importar cada hoja en su layer:

```css
/* global.css */
@import "./layers.css";
@import "./properties.css";                                    /* @property — fuera de layers */
@import "@roman-dev/tokens/dist/tokens.css" layer(tokens);
@import "./reset.css" layer(reset);

@layer base {
  *, *::before, *::after { box-sizing: border-box; }
  html {
    font-family: var(--rd-semantic-type-family-body);
    color: var(--rd-semantic-color-text-primary);
  }
}
```

- **Pros:** predecible, nativo sin tooling, elimina `!important` como solución
- **Contras:** relativamente nuevo (2022, soporte ≥ Chrome 99), requiere disciplina inicial
- **Cuándo:** design systems, proyectos que mezclan CSS de múltiples fuentes (reset + tokens + componentes + utilidades)

### Utility-first / Atomic CSS (Tailwind, UnoCSS)

Clases de una sola propiedad aplicadas directamente en el markup. El CSS resultante es un conjunto fijo de utilidades — no crece con el proyecto.

```html
<button class="bg-blue-500 px-4 py-2 rounded text-white hover:bg-blue-600 focus:ring-2">
  Comprar
</button>
```

- **Pros:** el bundle de CSS no crece con el tiempo, sin nombrar nada, consistencia de valores forzada por el sistema de tokens, purging automático (solo genera lo que usás)
- **Contras:** markup verbose difícil de leer en componentes complejos, curva de aprendizaje de las clases
- **Cuándo:** equipos que priorizan velocidad, proyectos con design tokens bien definidos, cuando el dinamismo se maneja con clases condicionales

## Patrones de implementación avanzados

### Design Tokens — 3 capas

El sistema de tokens más robusto usa tres capas con roles distintos:

```
primitives/   →  valores RAW sin semántica
                 --rd-color-neutral-900: #212529
                 --rd-dimension-4: 4px

semantic/     →  ROLES — los únicos que se usan en componentes
                 --rd-semantic-color-text-primary: var(--rd-color-neutral-900)
                 --rd-semantic-space-md: var(--rd-dimension-16)

component/    →  tokens de scope de componente (opcional)
                 --rd-button-bg: var(--rd-semantic-color-bg-primary)
```

**Regla estricta:**

```css
/* ✅ Correcto */
color: var(--rd-semantic-color-text-primary);

/* ❌ Prohibido — rompe el sistema de theming */
color: var(--rd-color-neutral-900);
color: #212529;
```

El dark mode se implementa sobreescribiendo solo los tokens semánticos:

```css
:root[data-theme="dark"] {
  --rd-semantic-color-bg-base:      var(--rd-color-neutral-950);
  --rd-semantic-color-text-primary: var(--rd-color-neutral-50);
}
```

La customización de marca por proyecto sobreescribe solo semánticos, nunca primitivos:

```css
/* brand.css — en el consumidor, no en el paquete de tokens */
@import "@roman-dev/tokens/dist/tokens.css";

:root {
  --rd-semantic-color-text-primary:   #1a0a2e;
  --rd-semantic-color-bg-base:        #faf8ff;
}
```

### `@property` — tokens interpolables

Para animar custom properties de color en transitions, el browser necesita saber el tipo. `@property` lo declara:

```css
@property --rd-semantic-color-text-primary {
  syntax: "<color>";
  inherits: true;
  initial-value: #212529; /* fallback si el token no resuelve */
}
```

Sin `@property`, `transition` en una custom property de color no interpola — hace un salto abrupto.

### Container Queries — responsive interno

El responsive de componentes no debería depender del viewport sino del espacio disponible. Container queries lo hacen posible:

```css
:host {
  display: block;
  container-type: inline-size; /* el componente es un contexto de container */
}

@container (min-width: 480px) {
  .layout {
    grid-template-columns: 1fr 1fr; /* responde a su contenedor, no al viewport */
  }
}
```

**Regla:** media queries solo en `global.css` para escala raíz. Dentro de componentes, siempre container queries.

### Logical Properties — soporte RTL

Logical properties remplazan las físicas (`left`, `right`, `top`, `bottom`) por las lógicas (`inline`, `block`), habilitando soporte RTL sin código adicional:

| Evitar | Usar |
|---|---|
| `margin-top` / `margin-bottom` | `margin-block` |
| `margin-left` / `margin-right` | `margin-inline` |
| `padding-left` / `padding-right` | `padding-inline` |
| `width` | `inline-size` |
| `max-width` | `max-inline-size` |
| `border-left` | `border-inline-start` |

## Comparativa de estrategias

| Estrategia | Scope | Runtime | Type safe | Dinamismo | Setup |
|---|---|---|---|---|---|
| BEM | Manual | No | No | Manual | Mínimo |
| CSS Modules | Automático | No | Parcial | No | Bajo |
| Scoped (Vue) | Automático | No | No | No | Mínimo |
| CSS-in-JS runtime | Automático | Sí | Sí | Total | Medio |
| CSS-in-JS zero-runtime | Automático | No | Sí | Build-time | Alto |
| CSS Layers | Global ordenado | No | No | No | Bajo |
| Utility-first | Global atómico | No | Con plugin | Condicional | Medio |

---

## Recomendación por contexto

| Contexto | Estrategia |
|---|---|
| React + SSR (Next.js) | CSS Modules o vanilla-extract |
| Design system compartido | CSS Layers + tokens 3 capas + vanilla-extract |
| App client-side intensiva en estado | CSS-in-JS runtime (styled-components / Emotion) |
| Velocidad máxima de desarrollo | Tailwind |
| Sin bundler / legacy | BEM |
| Vue | Scoped styles + CSS custom properties |
| Multi-marca / theming | Design tokens semánticos + `@layer` |
