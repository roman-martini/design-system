## Advertencias (35)

### `component-usa-primitive-de-color` — 13

Permitido por ADR-003 («component puede referenciar semantic o primitives»); se informa porque un primitive no responde al theme.

**Deliberado probable — 12** · `packages/tokens/src/component/badge.json`
Los pares `solid-bg`/`solid-text` de las 6 variantes del badge (`danger`, `info`, `neutral`, `primary`, `success`, `warning`) referencian primitivas (`{color.red.600}`, `{color.white}`, `{color.neutral.900}`, etc.). Un badge sólido con texto fijo sobre fondo saturado fijo entre themes es una decisión de diseño común y coherente: el par viaja junto y su contraste no depende del theme. Se recomienda **documentar la intención** (comentario en `badge.json` o requirement en la spec del componente) para que la advertencia quede saldada y no se reevalúe en cada auditoría.

**Revisar — 1** · `component.switch.thumb.bg` → `{color.white}` · `packages/tokens/src/component/switch.json`
Mismo patrón que el `bg-off` de checkbox/radio que `aaa-051` corrigió por no ser theme-aware: en dark el thumb queda blanco fijo. Puede ser deliberado (thumb blanco sobre track coloreado funciona en ambos themes), pero es exactamente la familia de bug que la Parte G ya corrigió dos veces. **Candidato a revisión visual del PO en la Parte H** — decidir primero cuál es la verdad (regla de `aaa-049`), no conectar a ciegas.

### `semantic-sin-referencia` — 22

Tokens semantic con valor literal en vez de referencia a primitivas.

**Deliberado o sin primitiva posible — 16**

- `semantic.z-index.*` (13) · `z-index.json`: no existen primitivas de z-index; la escala misma es el valor, fijada por la spec (13 niveles, `aaa-009`). Correcto como está.
- `semantic.radius.full` = `9999px` · `space.json`: idiom CSS para radio total; no hay primitiva que lo represente.
- `semantic.effect.blur.overlay` = `8px` · `effect.json`: la propia spec `design-tokens-package` fija el formato literal `<n>px`.
- `semantic.color.bg.overlay` = `rgba(0, 0, 0, 0.5)` · `color.json`: Style Dictionary no compone color + opacity por referencia; cambiarlo exige otra técnica (`color-mix`), no una referencia.

**Conectables a primitivas existentes — 6** · `motion.json`

Los 6 tokens `semantic.motion.transition.*` duplican como literal valores que ya existen como primitivas:

| Token           | Literal                                   | Composición exacta disponible                                       |
| --------------- | ----------------------------------------- | ------------------------------------------------------------------- |
| `fast`          | `100ms cubic-bezier(0, 0, 0.2, 1)`        | `{motion.duration.fast} {motion.easing.ease-out}`                   |
| `normal`        | `200ms cubic-bezier(0, 0, 0.2, 1)`        | `{motion.duration.normal} {motion.easing.ease-out}`                 |
| `slow`          | `300ms cubic-bezier(0, 0, 0.2, 1)`        | `{motion.duration.slow} {motion.easing.ease-out}`                   |
| `spring`        | `200ms cubic-bezier(0.34, 1.56, 0.64, 1)` | `{motion.duration.normal} {motion.easing.spring}`                   |
| `overlay-enter` | `250ms cubic-bezier(0, 0, 0.2, 1)`        | duración 250ms **no existe** como primitiva; easing sí (`ease-out`) |
| `overlay-exit`  | `150ms cubic-bezier(0.4, 0, 1, 1)`        | duración 150ms **no existe** como primitiva; easing sí (`ease-in`)  |

Conectar los 4 primeros es mecánico (mismos valores, cero cambio visual) y de paso des-huérfana `motion.easing.ease-in` y `motion.easing.spring`. Para `overlay-enter`/`overlay-exit` hay que decidir si se agregan primitivas `motion.duration` 150/250 o se deja el literal (la deriva duración+easing por separado ya está mitigada por el requirement de la spec que fija su formato). **Candidato a ítem chico de la Parte H.**

### Inventario deliberado — 118 (se conserva)

**Primitivas — 67.** Escalas completas por diseño; un tramo sin consumidor no es defecto (es la cobertura que un consumidor externo del package espera):

- `color.*` (29) · `primitives/color.json`: la escala `orange` completa (11), tramos de `purple` (4), `teal` (4), `yellow` (4), `red` (2), `green` (2), `blue.100`, `color.black` y `color.neutral.0`. Nota: `color.neutral.0` = `#ffffff` duplica a `color.white` — si alguna vez se poda, es el único candidato con justificación (dos nombres para el mismo valor).
- `dimension.*` (7), `font.*` (15), `opacity.*` (10), `shadow.*` (3), `motion.*` (3) · `primitives/`: extremos y pasos intermedios de escalas en uso. Nota: la categoría `font.letter-spacing` (6 tokens) no tiene ningún consumidor — inventario válido, pero es una categoría entera, no un tramo.

**Semantic — 51.** API pública del package para apps consumidoras; el kit no es su único cliente:

- `semantic.z-index.*` (12 de 13) · `z-index.json`: los 13 niveles son spec (`aaa-009`). El kit no los consume **por diseño**: sus overlays usan el top layer del Popover API y no necesitan z-index (documentado en `packages/components/src/lib/menu/menu.css:9` y `select/select.css:87`). La escala existe para el layering de la app consumidora.
- `semantic.font.*` (16) · `typography.json`: el sistema tipográfico (familias, tamaños de heading/body/code, line-heights, weights) es para las apps; los componentes del kit no tipografían páginas.
- `semantic.space.negative.*` (5 de 6) · `space.json`: escala entregada completa a propósito en `aaa-037` (HU-018, D del PO); `sm` ya tiene consumidor (avatar).
- `semantic.color.*` (10) · `color.json`: `bg.success/warning/info` + sus `-hover` (6, fondos sólidos de status aún sin componente que los use), `border.subtle` (parte del contrato de jerarquía `subtle < default < strong` verificado por gate — no es podable), `icon.inverse`, `icon.primary`, `text.tertiary`.
- `semantic.motion.transition.fast/normal/slow/spring` (4) · `motion.json`: presets de transición para consumidores (el kit solo usa `overlay-enter`/`exit`). Su mejora es la conexión a primitivas (ver Advertencias), no la poda.
- Extremos de escala (4): `semantic.radius.2xl`, `semantic.space.2xl/3xl`, `semantic.shadow.input`.

### Deuda real — 66 (insumo de la Parte H)

Todos en la capa `component.*`: tokens declarados que el CSS del componente no consume. La regla de `aaa-049` aplica a cada grupo: **primero decidir cuál es la verdad (token o render), después conectar o retirar** — adoptar el token a ciegas mete un rediseño dentro de un fix.

**1. `component.alert.*` — 24 tokens de un componente que no existe** · `component/alert.json`
El kit tiene 24 componentes y ninguno es Alert (`packages/components/src/lib/` no tiene `alert/`); `alert.json` es el único archivo de tokens de componente sin componente. Decisión del PO: si Alert entra al roadmap, los tokens son spec anticipada y se conservan; si no, el archivo se retira. No es un fix de CSS.

**2. `component.button.*` — 26** · `component/button.json`

- **Discrepancia token↔render con valor distinto (1)**: `component.button.font-weight` declara `{semantic.font.weight.button}` = `{font.weight.semibold}` (600), pero `button.css` renderiza con `var(--ds-font-weight-medium)` (500). El caso `aaa-049` de nuevo: el token dice una cosa y el botón pinta otra. Decidir la verdad (¿el botón es medium o semibold?) antes de conectar.
- **Bypass de capa en 4 variantes (23)**: los tokens de color de `primary` (5), `secondary` (5), `ghost` (5), `link` (5), `danger-ghost.bg/border` (2) y `danger.border` (1) están declarados, pero `button.css` consume los semantic directamente (`--ds-semantic-color-bg-primary`, etc.). Inconsistente con `danger` y `outline`, que sí pasan por la capa component. Hoy no hay divergencia visual (los tokens alias a los mismos semantic), pero la capa muerta es exactamente donde la Parte G encontró render contradiciendo al token.
- **Focus ring propio sin uso (2)**: `focus-ring-color`, `focus-ring-width` — ver grupo 4.

**3. Estados hover declarados y no renderizados — 3** · `component/checkbox.json`, `component/radio.json`
`checkbox.bg-off-hover`, `checkbox.bg-on-hover`, `radio.bg-off-hover`: los tokens prometen un estado hover del control que el CSS no pinta. O se implementa el hover o se retiran.

**4. Focus ring por componente vs sistema — 6** · `button.json`, `checkbox.json`, `input.json`, `radio.json`, `switch.json`
`component.{button.focus-ring-color, button.focus-ring-width, checkbox.focus-ring, input.focus-ring, radio.focus-ring, switch.focus-ring}`: todos los componentes resuelven el focus con `var(--ds-semantic-shadow-focus)` (p. ej. `checkbox.css:90`), que es el modelo del sistema (WCAG 2.4.7, un solo anillo consistente). Los tokens per-componente son una capa de personalización que nadie usa. Decisión única para los 6: se retira la capa o se adopta como API de theming del focus — no conectar componente por componente.

## Limitaciones del detector

1. **Consumo desde TS no detectado**: el script solo reconoce `var(--ds-…)`; las lecturas vía `getPropertyValue('--ds-…')` / `readCssNumber(…, '--ds-…')` no cuentan como consumo. Produjo los 6 falsos positivos listados. Mejora concreta: agregar al escaneo el patrón de custom property entre comillas en `.ts`. Es un cambio a `.claude/skills/audit-tokens/scripts/audit-tokens.mjs` — fuera del alcance de esta corrida (la skill audita, no arregla).
2. **El consumo se mide solo en `packages/components/src`**: tokens consumidos únicamente por playground o stories cuentan como huérfanos (fuera de alcance por HU-032; sesgo conocido y aceptado).
3. **La composición duración+easing** de `semantic.motion.transition.*` se compara a mano contra `primitives/motion.json`; el script no la verifica.
